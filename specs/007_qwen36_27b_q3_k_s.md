# 007 - Qwen3.6-27B Q3_K_S con llama.cpp

## Objetivo

Agregar una variante Q3 de Qwen3.6-27B en `llms` para medir si el offload
completo mejora la velocidad frente a IQ4_XS. No reemplaza ni borra IQ4 o Q6.
Los tres Deployments se versionan con `replicas: 0` y comparten la unica GPU de
forma excluyente.

## Artefacto verificado

La revision fijada de `unsloth/Qwen3.6-27B-GGUF` no contiene `IQ3_M`. Se eligio
su `Q3_K_S` oficial en lugar de usar una conversion reciente de terceros.

| Campo | Valor |
| --- | --- |
| Archivo | `Qwen3.6-27B-Q3_K_S.gguf` |
| Revision | `82d411acf4a06cfb8d9b073a5211bf410bfc29bf` |
| Tamano | `12,358,727,904` bytes, `11.510 GiB` |
| SHA-256 | `4afb4abcf0207a484b0d7e92c0421b74e8ce1c7a7250bb9d824b79288da68f20` |
| Arquitectura | `qwen35`, 64 capas, 27B parametros |
| Contexto nativo | 262,144 tokens |
| Licencia | Apache-2.0 |

La fuente de tamano y SHA-256 es el objeto LFS publicado por la API de
Hugging Face para esa revision.

## Configuracion

```text
--n-gpu-layers auto
--fit on
--fit-target 2048
--ctx-size 65536
--parallel 1
--cache-type-k f16
--cache-type-v f16
--no-kv-offload
--cache-ram 0
--ctx-checkpoints 4
```

El archivo es aproximadamente 2.87 GiB menor que IQ4_XS. Se espera que sus
65 capas cargables entren en CUDA conservando cerca de 2 GiB de margen, pero
la aceptacion exige confirmarlo en los logs del arranque. El KV F16 permanece
en RAM y reserva 4 GiB para los 16 bloques de full attention a 65K.

## Descargar sin interrumpir IQ4

El Job no solicita GPU:

```bash
set -euo pipefail

kubectl apply -f kubernetes/llama-service/pvc-q3.yaml
kubectl apply -f kubernetes/llama-service/deployment-q3.yaml
kubectl apply -f kubernetes/llama-service/service-q3.yaml
kubectl -n llms delete job download-qwen36-27b-q3-k-s --ignore-not-found
kubectl apply -f kubernetes/llama-service/model-download-q3-job.yaml
kubectl -n llms wait \
  --for=condition=Complete job/download-qwen36-27b-q3-k-s \
  --timeout=4h10m
kubectl -n llms logs job/download-qwen36-27b-q3-k-s
```

No ejecutar `kubectl apply -k kubernetes/llama-service` durante esta descarga
si IQ4 esta activo: los manifiestos conservan replicas cero y esa aplicacion
reconciliaria `llama-server` a cero.

## Cambiar de IQ4 a Q3

```bash
set -euo pipefail

sudo systemctl stop hermes-gateway.service
kubectl -n llms scale deployment/llama-server --replicas=0
kubectl -n llms wait --for=delete pod -l app=llama-server --timeout=5m

for deployment in \
  vllm vllm-big-model vllm-small-model llama-server llama-server-q6; do
  test "$(kubectl -n llms get deployment/$deployment \
    -o jsonpath='{.spec.replicas}')" = 0
done
for scaledobject in vllm-big-model vllm-small-model; do
  test "$(kubectl -n llms get scaledobject.keda.sh/$scaledobject \
    -o jsonpath='{.metadata.annotations.autoscaling\.keda\.sh/paused-replicas}')" = 0
  test "$(kubectl -n llms get scaledobject.keda.sh/$scaledobject \
    -o jsonpath='{.status.conditions[?(@.type=="Paused")].status}')" = True
done

kubectl -n llms scale deployment/llama-server-q3 --replicas=1
kubectl -n llms rollout status deployment/llama-server-q3 --timeout=35m
kubectl -n llms logs deployment/llama-server-q3 --tail=300
```

Confirmar build b10156, arquitectura `qwen35`, contexto 65,536, capas CUDA,
buffers CPU/CUDA, Flash Attention y ausencia de OOM. Registrar VRAM libre y RSS.

## Resultados medidos

El 29 de julio de 2026, llama.cpp b10156 cargo Q3_K_S sin ajustar el offload:

| Campo | Resultado |
| --- | ---: |
| Capas CUDA | 65/65 |
| Buffer de modelo CUDA | 11,254.73 MiB |
| Buffer de modelo CPU | 521.00 MiB |
| Compute buffer CUDA | 388.01 MiB |
| KV F16 en CPU | 4,096.00 MiB |
| Margen proyectado por `--fit` | 3,090 MiB |
| VRAM libre despues del benchmark largo | 2,982 MiB |
| RSS del pod despues del benchmark largo | 5,138 MiB |

Comparacion reproducible contra IQ4_XS con `--fit-target 2048`:

| Variante | Prompt | Prompt tok/s | Generacion tok/s | Tiempo total |
| --- | ---: | ---: | ---: | ---: |
| IQ4_XS | 3,744 | 897.22 | 7.78 | 37.10 s |
| Q3_K_S | 3,744 | 1,113.46 | 13.24 | 22.71 s |
| IQ4_XS | 31,454 | 828.33 | 3.46 | 111.97 s |
| Q3_K_S | 31,454 | 976.99 | 5.49 | 78.84 s |

Q3_K_S mejora decode aproximadamente 70% con contexto corto y 59% con 31.5K
tokens. El tiempo total baja 39% y 30% respectivamente. No hubo OOM, errores
CUDA ni reinicios. Flash Attention y los kernels fusionados de Gated DeltaNet
quedaron habilitados. LiteLLM respondio HTTP 200 y `hermes -z` respondio `OK`.

Estos datos miden rendimiento, no calidad. Mantener IQ4 disponible hasta
comparar razonamiento, coding y tool calling en conversaciones reales.

## Volver a IQ4

```bash
sudo systemctl stop hermes-gateway.service
kubectl -n llms scale deployment/llama-server-q3 --replicas=0
kubectl -n llms wait --for=delete pod -l app=llama-server-q3 --timeout=5m
kubectl -n llms scale deployment/llama-server --replicas=1
kubectl -n llms rollout status deployment/llama-server --timeout=35m
hermes config set model.default qwen3.6-27b
sudo systemctl start hermes-gateway.service
hermes -z 'Responde exactamente: OK'
```

No borrar PVC durante el cambio. Para volver a vLLM, el rollback del spec 005
detiene IQ4, Q3 y Q6 antes de restaurar el consumidor GPU anterior.
